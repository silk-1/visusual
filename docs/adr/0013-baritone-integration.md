# ADR-0013: Baritone как внешний движок, а не как скопированный код

**Статус:** принято
**Дата:** 2026-11-16
**Контекст:** запрос владельца «перейдём на Baritone, он нам нужен как кислород для автоматизации»

## Решение

SilkVis **не содержит** код Baritone и **не зависит** от него на этапе компиляции.

Игрок ставит Baritone сам, обычным способом: кладёт его jar в `mods/` рядом с SilkVis.
SilkVis находит его в рантайме через `Class.forName` и управляет им через публичный API
Baritone: `BaritoneAPI.getProvider().getPrimaryBaritone()` и далее
`getCustomGoalProcess()`, `getMineProcess()`, `getFollowProcess()`, `getExploreProcess()`.

Весь мост — один файл: `client/baritone/BaritoneBridge.java`. Модель задач и статуса
(`automation/baritone/`) не знает про Baritone вообще и проверяется `selfCheck`.

## Почему не копирование

Рассматривалось и отклонено. Baritone — 367 java-файлов и 20 миксинов, со своим
инструментом сборки (`unimined`, `buildSrc`, Proguard). Перенос означал бы:

* переезд целого мода в репозиторий и его починку под наш билд;
* отмену правила «никаких миксинов» (ADR-0002, AGENTS.md);
* потерю независимости: правки Baritone пришлось бы тянуть руками при каждом его обновлении.

Вызов по API даёт **весь** функционал Baritone без единой скопированной строки.

## Почему без compile-зависимости

`Class.forName` вместо `compileOnly baritone`:

* **плюс:** без Baritone мод грузится штатно, вкладка честно говорит «не установлен»;
* **плюс:** не нужно собирать Baritone под каждую нашу сборку (у него своя цепочка, к
  которой у нас нет доступа);
* **минус:** ошибки только в рантайме, компилятор не проверяет имена методов.

Минус принят, потому что компенсируется: все имена API сверены с исходниками ветки
`1.21.10` и выписаны в javadoc `BaritoneBridge`, а любая ошибка рефлексии превращается в
`BaritoneStatus.BROKEN` с причиной для лога — не в падение клиента.

## Лицензии

* Baritone — **LGPL-3.0**. Вызов библиотеки не делает наш код производным от неё.
* SilkVis остаётся **Apache-2.0**. Смена лицензии не требуется.
* Копирование кода Baritone потребовало бы LGPL для всего SilkVis, и это **невозможно**:
  в проекте 43 файла под SOUP-1.0 (разрешение Padej_ выдано лично владельцу проекта и не
  позволяет перелицензировать чужой код) — см. `THIRD_PARTY_NOTICES.md`.

## Что видит игрок

Отдельная вкладка **BARITONE** (не режим вкладки AUTOMATION: два разных движка, и игрок
должен видеть, кто из них работает). Первая строка — состояние:

| состояние | что написано | что делать |
|---|---|---|
| `MISSING` | baritone: not installed | положить jar Baritone для 1.21.10 в `mods/` |
| `BROKEN` | baritone: unusable (причина) | версия Baritone не подходит |
| `READY` | baritone: idle / baritone: <процесс> | можно запускать задачи |

Кнопки задач, которым нужна цель, пока заблокированы — задача без координаты упала бы
молча. «Стоп» работает всегда.

## Почему команды, а не объекты API

Первая версия вызывала типизированный API: `setGoalAndPath(new GoalBlock(...))`,
`follow(String)`. Она скомпилировалась, прошла чеки и упала в игре:

```
NoSuchMethodException: baritone.api.process.IFollowProcess.follow(java.lang.String)
```

Причина структурная, не опечатка: чтобы вызвать типизированный API, в сигнатурах нужно
назвать классы Minecraft — `Predicate<Entity>`, `BlockOptionalMeta`, `GoalBlock`. Эти классы
принадлежат сборке Baritone под конкретную версию Minecraft. В jar для другой версии методы
есть, а таких типов параметров нет, и рефлексия не может к ним привязаться.

Поэтому мост работает через **команды**: `ICommandManager.execute("goto 10 64 -20")`.
Там только `String` и `boolean` — нечего обфусцировать и нечему разъезжаться. Это тот же
слой, которым пользуются чат-команды самого Baritone.

| задача | команда |
|---|---|
| GOTO / EXCAVATE | `goto x y z` |
| MINE | `mine <blocks...>` или `mine <n> <blocks...>` |
| COLLECT | `thisway` |
| FOLLOW | `follow player <name>` |
| EXPLORE | `explore` |
| STOP / CANCEL | `cancel` |

Формы аргументов сверены с `MineCommand`/`FollowCommand` из исходников Baritone, а не
взяты по памяти:

* `mine` берёт **необязательное** число первым аргументом (`getAsOrDefault(Integer.class, 0)`),
  поэтому ноль надо не передавать, а опускать: `mine 0 diamond_ore` Baritone поймёт как
  «копать ноль блоков»;
* `follow` принимает группу в единственном числе — `follow player <ник>` (во множественном
  числе это `follow players`, без ника, «за любым игроком»).

Проверяется чеком `automation: every baritone task maps to a real chat command`: имена
сверяются со списком команд из исходников Baritone, и выдуманная команда падает в чеке, а
не у игрока при первом нажатии.

## Какой jar нужен игроку

**`baritone-api-fabric`**, не `standalone`. У `api` публичный API сохранён, у `standalone`
внутренности обфусцированы — через рефлексию к нему не подступиться. Проверено по
документации сборки Baritone, а не по догадке.

Версия должна быть **той же, что у SilkVis**: в коде используются имена из ветки `1.21.10`,
и сборки Baritone под другие версии Minecraft их не содержат. Ошибка версии не ломает игру —
мост сообщает `BROKEN`, печатает причину в лог и во вкладку.

## Что не сделано и почему

* **Свой движок не удалён.** 6 целей, A*, 37 чеков остаются в коде и выключены. Удаление
  сделало бы откат дорогим, а вреда от неиспользуемого кода нет. Решение об удалении —
  отдельное.
* **Не все задачи подключены к кнопкам.** Работает «Стоп»; остальным нужна цель (блок под
  прицелом или координата), и её выбор — следующий шаг. Кнопка, которая молча ничего не
  делает, хуже отсутствующей.

## Дополнение от 2026-11-17: вкладка стала меню, а не списком кнопок

Первая версия вкладки рисовала по кнопке на каждый элемент `BaritoneTask` — девять кнопок в
два столбца, где «выкопать область» стоял рядом с «отменить». Игрок, который искал «копать
алмазы», видел стену кнопок, из которых работает одна, и не находил нужную.

Решение: вкладка — это **меню из пяти задач** в том порядке, в котором их ищут: «Копать»,
«Идти», «Следовать», «Исследовать», «Стоп». Две задачи открывают свою страницу, потому что
им нужно поле ввода, а не одна кнопка:

* **«Копать»** — сетка руд с мультивыбором (`automation/baritone/BaritoneOre.java`), лимит
  шагом 16 и кнопка «Начать», которая отправляет `mine [n] <блоки...>`. Выбор хранится в
  `BaritoneMinePlan` внутри рантайма, то есть переживает закрытие окна;
* **«Следовать»** — поле ника, кнопка отправляет `follow player <ник>`.

Список блоков больше **не** на главной странице вкладки: он живёт только внутри «Копать».
Руды — фиксированный список с русскими и английскими названиями в lang-файлах, а не весь
реестр блоков: в реестре тысяча записей, и она превращает выбор в поиск по буквам.

Под меню всегда видна строка «Последняя команда»: `execute` возвращает `boolean`, и если
Baritone отказал, игрок видит отправленную строку и причину, а не тишину.

`EXCAVATE`, `COLLECT` и `GOTO_ALLOW_BREAK` остаются в `BaritoneTask` (их id — ключи логов и
конфига), но кнопок у них пока нет: у `EXCAVATE` команда `goto`, то есть это не выкапывание
области, и выставлять такую кнопку игроку нельзя.

## Дополнение от 2026-11-17 (2): вкладка стала каталогом плиток

Предыдущее дополнение (меню из пяти задач) заменено. Причина: пять задач закрывали
`mine`, `goto`, `follow`, `explore`, `cancel` — пятую часть того, что умеет Baritone, — и
чтобы добраться до остального, игрок всё равно возвращался в чат. «Визуальное меню» из пяти
кнопок остаётся списком, просто короче.

Теперь вкладка собрана из каталога:

* `automation/baritone/BaritoneAction.java` — 20 плиток: команда, раздел, иконка, тип
  аргумента, значения по умолчанию. Экран рисует разделы, плитки и формы **из этого списка**,
  поэтому новая команда стоит одной строки в enum, а не новой страницы, метода и двух ключей
  в каждом языке.
* `automation/baritone/BaritoneBlock.java` — 21 запись: руды (алмаз, железо, уголь, медь,
  золото, редстоун, лазурит, изумруд, кварц, незерское золото, древние обломки) и массовые
  блоки (камень, земля, песок/гравий, брёвна, листва, обсидиан, незерак, камень Края,
  снег/лёд, глина). Первый id записи — её иконка: у каждого такого блока есть block item.
* `automation/baritone/BaritoneParams.java` — состояние одной формы: отмеченные блоки, числа,
  текст, точка. Живёт в рантайме (`EnumMap` по действию), поэтому переживает закрытие окна.

Разделы меню: **Движение** (идти в точку, идти к блоку, идти вперёд, тоннель, следовать за
игроком, на поверхность, развернуться), **Копать** (копать, ферма, собрать дроп),
**Строить** (точка 1, точка 2, сброс выделения, залить выделение, построить схематику),
**Поиск** (исследовать, найти блоки), **Управление** (пауза, продолжить, остановить всё).

Формы по типу аргумента — их всего восемь, и это весь код экрана:

| тип | что показывает |
|---|---|
| `NONE` | только кнопку «Начать» |
| `POINT` | координаты из прицела (или из-под ног) и подсказку |
| `SINGLE_BLOCK` | сетку блоков с одиночным выбором |
| `BLOCKS` | сетку блоков с мультивыбором |
| `BLOCKS_AND_COUNT` | то же плюс лимит шагом 16 |
| `NUMBER` | одно число с шагом 10 (дальность, диапазон) |
| `NUMBERS` | три числа (высота, ширина, глубина тоннеля) |
| `TEXT` | поле текста (ник игрока, имя схематики) |

Сетка блоков больше **не** появляется ни на главной странице вкладки, ни в других вкладках:
она есть только внутри действий, которые принимают блоки (`mine`, `find`, `goto <block>`,
`sel set`).

### Иконки

Плитка показывает иконку предмета и всегда — название рядом. Иконка идёт через
`Painter.itemIcon`, у которого по умолчанию пустая реализация, а `VanillaPainter` делает
`Registries.ITEM.get(...)` + `DrawContext#drawItem`. Оба вызова — единственные
версионно-зависимые места, они в try/catch, и первая же ошибка выключает иконки до конца
сессии: плитка остаётся с подложкой и названием. Иконка — украшение, никогда не информация.

### Диагностика вместо догадок

Причина «кнопки не работают» раньше не была видна нигде, кроме лога. Теперь в вкладке есть
страница **«Диагностика»**: она заново проходит цепочку моста и печатает по строке на шаг —
класс API, провайдер, экземпляр Baritone, менеджер команд, метод `execute(String)`,
последняя ошибка. Первая отмеченная строка и есть причина: нет класса API — Baritone не
установлен, не поднялся провайдер — jar собран под другую версию Minecraft.

### Формы команд (сверены с исходниками Baritone)

| плитка | команда |
|---|---|
| Идти в точку | `goto <x> <y> <z>` |
| Идти к блоку | `goto <block>` |
| Идти вперёд | `thisway <distance>` — аргумент обязателен |
| Тоннель | `tunnel <height> <width> <depth>` |
| Следовать за игроком | `follow player <ник>` |
| На поверхность | `surface` |
| Развернуться | `invert` |
| Копать | `mine <blocks...>` или `mine <n> <blocks...>` |
| Ферма | `farm` или `farm <range>` |
| Собрать дроп | `pickup` |
| Выделение | `sel pos1` / `sel pos2` / `sel clear` |
| Залить выделение | `sel set <block>` |
| Построить схематику | `build <filename>` |
| Исследовать | `explore` |
| Найти блоки | `find <block> [...]` |
| Пауза / Продолжить / Стоп | `pause` / `resume` / `cancel` |

`BaritoneTask` (плоская модель «задача = одна строка») остаётся: её id — ключи логов и
конфига, и на ней держатся чеки моста. Экран её больше не использует.

## Дополнение от 2026-11-17 (3): прокрутка, координаты, две кнопки «Начать»

Три правки по отчёту из игры:

1. **Прокрутка панели настроек.** `rebuildSettings` считала высоту контента по уже
   сдвинутым на `offset` виджетам, то есть высота **уменьшалась** по мере прокрутки:
   `maxOffset` схлопывался быстрее, чем игрок доскролливал, и низ длинной страницы (сетка
   руд вместе с «Начать») не открывался никогда. Теперь к высоте прибавляется текущий
   `offset`, поэтому она не зависит от положения прокрутки.
2. **Координаты полями.** `POINT` больше не «только прицел»: три поля X/Y/Z, при
   открытии заполненные целью прицела, плюс кнопка «Взять из прицела». Числа проверяются
   (`-?\d{1,9}`), невалидное поле = `command() == null` = кнопка выключена.
3. **«Начать» дважды.** Форма руд — одиннадцать строк плиток; кнопка под ними читалась как
   «кнопки нет». Кнопка стоит и над полями, и под ними, обе ведут в один и тот же
   `startBaritoneAction`; строка «Команда: …» показывается у верхней.
