# ADR-0012. Автоматизация: свой движок по образцу Baritone

- Статус: **принято**
- Дата: 2026-11-15
- Связано: AGENTS.md (правило 7), ADR-0009, AUTO-01…AUTO-04, PERF-02

## Контекст

Владелец попросил сделать автоматизацию «грамотно, за основу взять Baritone, а то, чего
в Baritone нет, написать самому». До этой сборки вкладка «Автоматизация» была заглушкой
`planned_note`, а `AutomationCatalog` держал 22 записи `A01…A22` со статусом `PLANNED`.

Ограничения проекта, которые определили решение:

- **Никаких миксинов** (AGENTS.md). Значит, нельзя подменять `ClientPlayerEntity.tick` или
  писать в пакеты: ввод идёт через те же пути, что у ванильного игрока.
- **Никаких новых зависимостей.** Baritone как артефакт не подключается.
- **Лицензионная чистота.** Baritone под LGPL-3.0; копировать его код в этот репозиторий
  нельзя. Поэтому берётся *архитектура*, а не строки.
- **Всё выключено по умолчанию** (правило 7) и **один слой адаптера** к `net.minecraft.*`.
- **Проверяемость без запуска игры**: ядро должно гоняться в `selfCheck`.

## Решение

**Слои.** `silkvis.automation` не знает про Minecraft вообще:

```
Goal (A01, A03, A04, A19, A21, A22)
  └─ plan(Snapshot, Budget) → List<Step>      // чистые данные
AutomationEngine                              // предохранители, один goal, бюджет на тик
  └─ Executor.execute(Step, AutomationMode)   // единственное место с вводом
```

- `Snapshot` — снимок мира на тик: позиция, здоровье, еда, измерение, `Grid`, сущности,
  хотбар, `blockId`, `breakTicks`, `cropRipe`. Цели не держат ссылок на живые объекты.
- `Step` — примитив (`GOTO`, `MINE`, `PLACE`, `LOOK`, `ATTACK`, `USE_ITEM`, `SELECT_SLOT`,
  `WAIT`). Цель никогда не ходит и не копает сама.
- `Movement` — A* по `Grid` с октильной эвристикой, ценой `PathCost` и `Budget`. Разрушение
  блока стоит `BREAK = 8.0`, то есть всегда дороже любого чистого перемещения: «дойди туда»
  обойдёт дом, а не пророет его. Диагональ запрещена через закрытый угол (`cornerOpen`).
- `AutomationEngine.tick` — сначала предохранители (здоровье, еда, опасность под ногами,
  враждебный моб в радиусе, ввод игрока, смена измерения), потом цель. Остановка всегда
  атрибутирована `StopReason`.
- `AutomationMode`: `OFF` / `HINT` / `MOVE` / `FULL`. `HINT` только планирует и показывает
  строку, `MOVE` не ломает и не ставит блоки (исполнитель проверяет режим повторно).

**Адаптер.** Два класса, и только они знают про `net.minecraft.*`:
`AutomationSnapshot` (чтение мира → `Snapshot`) и `AutomationExecutor` (шаг → ввод).
Ввод — `player.setYaw/setPitch` и `options.*Key.setPressed(...)` плюс
`interactionManager.attackBlock/updateBlockBreakingProgress/interactBlock/interactItem`.
Это те же вызовы, что делает ванильный ввод, поэтому сервер видит обычного игрока.

**Чего нет в Baritone, сделано своё:** `TreeFarmGoal` (заливка связки брёвен от выбранного
блока, сверху вниз, листва не трогается), `FarmGoal` (только спелые культуры, сразу
пересаживает), `CollectGoal` (пропускает предметы в лаве/огне), `SafetyGoal` (спиральный
выход из опасной зоны без копания), `AutomationCatalog` как единый источник статуса
«реализовано / запланировано».

**Чего нет намеренно:** стека целей (один goal — одна строка статуса — одна кнопка
«стоп»), чанк-лоадинга, паркура, схематик-строительства. Цель, которой это нужно, обязана
завершиться с причиной, а не пытаться.

## Последствия

- Автоматизация проверяема без игры: `FakeWorld` + `RecordingExecutor` дают 20+ чеков в
  `selfCheck` (стоимость, обход стены, дверь, лава, бюджет, режимы, остановки).
- Порог P1 из AGENTS.md («AUTO не раньше закрытого P1») закрыт решением владельца; вкладка
  больше не заглушка, но по умолчанию режим `OFF` и ничего не запускается.
- Каждый новый goal — это запись в `GoalRegistry` и в `IMPLEMENTED` каталога; чек
  `catalogMatchesRegistry` не даёт спискам разойтись.
