# Почему запуск долгий и как это измерить

«Запуск 5 минут» — это четыре разных процесса, которые легко перепутать. Пока не
известно, какой из них медленный, любая «оптимизация» — гадание. Поэтому сначала
измеряем, потом правим.

## 1. Что именно мерить

| # | Что | Как получить число | Норма |
|---|---|---|---|
| 1 | **Сборка** | `build.bat` печатает `[SilkVis] START …` и `[SilkVis] END …`, плюс Gradle сам пишет `BUILD SUCCESSFUL in Xs` | тёплая сборка без `clean` — 10–40 с; с `clean` — 40–90 с |
| 2 | **Первый запуск `runClient`** | от `> Task :runClient` до окна с меню | первый раз +1–3 мин (скачивание ассетов), дальше 30–60 с |
| 3 | **Запуск обычной игры из лаунчера** (мод в `mods`) | от нажатия «Играть» до меню | 20–60 с на 1.21.10 без тяжёлого модпака |
| 4 | **Загрузка мира** | от «Создать/войти» до появления HUD | 5–30 с |

`build.bat` теперь печатает время до и после Gradle — сравнение двух строк и есть ответ.

## 2. Если медленная сборка (пункт 1)

1. `build.bat` по умолчанию делает `clean build`: `clean` выбрасывает всё, включая
   remap-кэш. Для повседневной работы быстрее `build.bat jar` (без `clean`).
2. **Windows Defender** сканирует каждый файл в `build\` и `%USERPROFILE%\.gradle`.
   Это самая частая причина «сборка 2 минуты на Ryzen 7». Добавь исключения:

   ```powershell
   Add-MpPreference -ExclusionPath "F:\silkvis\build"
   Add-MpPreference -ExclusionPath "$env:USERPROFILE\.gradle"
   Add-MpPreference -ExclusionPath "F:\silkvis\.gradle"
   ```

   (Нужны права администратора. Исключения для папок сборки безопасны: это
   артефакты, а не исполняемые файлы из интернета.)
3. **OneDrive**: если проект лежит в синхронизируемой папке, каждый файл сборки
   отправляется в облако. `F:\silkvis` — хорошо, `C:\Users\…\OneDrive\…` — плохо.
4. **HDD vs SSD**: remap Loom читает тысячи мелких классов. На HDD это десятки секунд.
5. `gradle.properties` уже содержит `org.gradle.parallel=true`,
   `org.gradle.caching=true` и `-Xmx2G` для демона. Поднимать heap выше 3G смысла нет:
   Loom упирается в IO, а не в память.

## 3. Если медленный `runClient` (пункт 2)

- Первый запуск скачивает ассеты Minecraft (~200 МБ) в `%USERPROFILE%\.gradle\caches`.
  Это разово.
- Dev-клиент всегда медленнее обычного: Loom добавляет свой classpath и remap.
  Для проверки «как у игрока» правильнее собрать jar и запустить обычный клиент.
- Каждый `runClient` заново проходит `:compileJava` → `:processResources` → `:classes`.
  Если правил только ресурсы — быстрее `build.bat classes` и запуск из IDE.

## 4. Если медленная обычная игра (пункт 3)

SilkVis на старте делает немного: читает три JSON-файла, регистрирует HUD-элемент,
два бинда и один probe. Это миллисекунды — их видно в `latest.log` по строкам `[SilkVis]`.
Если игра грузится 5 минут, причина не в моде:

1. **Мало heap.** Лаунчер по умолчанию даёт 2 ГБ. Для 16 ГБ RAM поставь 4 ГБ:
   профиль → «Изменить» → Аргументы JVM → `-Xmx4G` (и `-Xms2G`).
2. **Render distance 32 и 200 модов** — это не «запуск мода», а загрузка мира.
3. **Defender** снова: Minecraft читает десятки тысяч файлов из `.minecraft\assets` и
   `mods`. Исключение для `.minecraft\assets` и `.minecraft\mods` даёт заметный выигрыш.
4. **Сетевые диски / антивирус сторонних производителей** (Kaspersky, ESET) — та же
   история, что с Defender.

## 5. Доказательство, а не догадка

Мод пишет отчёт об ошибке (вкладка «Настройки» → «Создать отчёт об ошибке»). В нём есть
`uptime`, `maxHeapMiB`, `cpus`, список модов и хвост `latest.log` с таймстампами.
Разница между строками лога

```text
[..:..:..] [main/INFO]: Loading 3 mods:
[..:..:..] [main/INFO]: [SilkVis] ...
```
и первой отрисовкой кадра — это и есть «сколько добавил мод». Если она меньше секунды,
мод к пятиминутному старту отношения не имеет.
